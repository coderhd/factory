## Review Focus

Inputs/conditions the spec implies but no task's own test names directly — each is pinned by a
step in the task that owns the code:

1. A `herdr tab create` payload that omits `root_pane` (malformed) — a reasonable operator
   expects the just-created pane to be torn down, not leaked. (Task 1, Step 3.)
2. A `github.token` mapping that carries a valid `env:` **and** a stray secret key (e.g. `value:`)
   — a reasonable operator expects rejection, not silent acceptance. (Task 1, Step 7.)
3. Two concurrent `collectArtifacts()` callers while a harness is still running — both must
   resolve with the *same* settled report and neither may short-circuit on a pre-settled result.
   (Task 2, Step 3.)
4. `deliverAnswer` when the harness prompt throws mid-answer — the operator expects the
   underlying cause surfaced, not a silent no-op. (Task 2, Step 5.)
5. A judge-infrastructure failure (no verdict file / crashed / blocked pane) — the operator
   expects the *structured* diagnosis on the failure record, not just a summary string.
   (Task 2, Steps 7–8.)
