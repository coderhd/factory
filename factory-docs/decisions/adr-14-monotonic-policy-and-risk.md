# ADR 14 — Policy is monotonic-narrowing down Org→Project→Work Order→Task; sensitive actions are runtime-checked

- **Status:** Accepted (2026-09-30)
- **Origin:** `coderhd/factory#22` ([E7.1] Policy/risk architecture; parent epic `coderhd/factory#7` — Factory Server v0.1 policy/recovery)
- **Design:** [policy-and-risk-model.md](../architecture/policy-and-risk-model.md) (capability list, decision semantics, attempt-widening worked examples, tier gates, recovery contract, threat model — the concrete spec sub-issue #23 implements to)
- **Extends:** design spec §12 (Interaction), §13 (Risk and Policy; §13.1 Risk Tiers, §13.2 Policy), §18 (bounded recovery); [ADR 13](adr-13-generic-decision-model.md) (generic DecisionModel seam; no provider model IDs in runtime semantics)
- **Consumes:** E1 `src/factory/state/store.ts` (`policy_decisions`, `EventLog`), `src/factory/domain/workOrder.ts` (`RiskTier`, `Attempt.failureHistory`); E3 `SchedulerPolicy.canAssign` (`PolicyVerdict`), `WorkerLease`
- **Follow-up:** #23 implements `src/factory/policy/policy.ts`, `src/factory/policy/risk.ts`, `src/factory/recovery/recovery.ts`, `tests/factory/e7-policy.test.ts` against this record (controller ruling R20: #22 owns the architecture, #23 the implementation)

## Context

Spec §13.2 fixes the shape: a policy hierarchy Organization → Project → Work Order → Task → Effective Policy, where "more specific policy can narrow authority but cannot expand beyond its parent"; capabilities are explicit (`repo.read`, `repo.write`, `branch.create`, `pr.create`, `ci.run`, `production.read`, `production.write`, `deploy.execute`, `secrets.read`); sensitive actions are checked at runtime; decisions are `ALLOW | DENY | REQUIRE_HUMAN`, recorded as durable events (task, action, risk, decision, rules, policy version); the MVP source of truth is versioned YAML. Spec §13.1 fixes the tiers: everything starts Yellow, Green is earned after evidence, Red never auto-promotes. Spec §18 fixes recovery: bounded, evidence-preserving, no blind universal retry, quota exhaustion is capacity not failure, emergency stop preserves state.

E1 and E3 merged without a runtime policy engine: E3's scheduler carries a `PolicyVerdict = 'ALLOW' | 'DENY' | 'REQUIRE_HUMAN'` seam (`SchedulerPolicy.canAssign`) that defaults to permissive, and E1 persists a `policy_decisions` collection that nothing fills. The v0.1 epic therefore needs, on paper, the concrete semantics #23 implements: exactly how narrowing composes, what each verdict means, how tiers interact with capabilities, and what the recovery engine may and may never do.

## Decision

1. **Policy is monotonic-narrowing with strictest-wins composition.** Per capability, decisions sit on a fixed restriction lattice — `DENY` > `REQUIRE_HUMAN` > `ALLOW` — and the effective decision at each level is the `tighter` fold of its parent's effective decision with its own: silence inherits down the chain, scopes **intersect** (a child may only remove resources), and if no level speaks the capability's root default applies. Consequently a child **cannot widen a parent**, proven on paper (induction over the chain: each level's contribution can only restrict; scope intersection is subset-closed): the full worked examples — a valid narrowing chain (Org→Project→WO→Task for `repo.write`) and three rejected attempts (a Task claiming `secrets.read: ALLOW`, a WO claiming `infra/**` paths, a WO/Task claiming production `deploy.execute: ALLOW`) — live in the design doc §7. Widening attempts are inert and recorded (`rules: 'widening-attempt'`), not fatal.

2. **Capabilities are closed-vocabulary and runtime-checked.** The nine spec §13.2 capabilities with fixed per-capability semantics — root default, sensitivity class, reversibility, and a **ceiling** (the most permissive decision any level may express; `production.write` and `secrets.read` cap at `REQUIRE_HUMAN`). Unknown capabilities are `DENY`. Workers never hold credentials; every consequential external action passes `check` at the Factory, and every check persists a `policy_decisions` row + `policy.decision` event in one transaction (fields per spec §13.2: task, action, risk, decision, rules, policy version).

3. **Decision semantics are fixed exactly.** `ALLOW` = proceed under Factory orchestration now (the only verdict that lets the scheduler assign or E6 act externally). `DENY` = refused durably; an explicit `DENY` anywhere on the matched scope is final below it, as are unknown capabilities and e-stop short-circuits. `REQUIRE_HUMAN` = parked pending an operator `APPROVAL` interaction (the engine creates the interaction); a matching, unspent, instance-bound approval consumes the verdict into `ALLOW` — the single sanctioned relaxation, which never overrides a `DENY` and lives outside the hierarchy, so humans can satisfy gates without ever becoming a widening policy level.

4. **Risk tiers keep their spec semantics, concretely.** Every Work Order starts `YELLOW` (human declaration aside); Green is **earned** — a durable per-change-class record pointing at a complete Evidence Bundle, green verification runs, a clean violation window, and an explicit operator sign-off; future WOs declare Green only by referencing it. `classifyRisk(wo) = tier-max(declared, inferred)` is monotone: inference never lowers the tier and can raise it (`YELLOW → RED` on the security taxonomy: auth, secrets, payments, PII, prod). Red never auto-promotes: the tier gate sets a per-tier restriction floor — every RED-classed check is `REQUIRE_HUMAN` at best; RED execution is model/capability-constrained with mandatory semantic + security verification and explicit human approval. The E4 routing risk vocabulary maps `GREEN↔low, YELLOW↔medium, RED↔high`.

5. **Recovery is bounded and evidence-preserving (spec §18 contract).** `recover(failure)` first *classifies* (closed enum incl. the spec §18.10 model events), then acts: bounded automatic retries (default 2 same-class, 3 total Attempts per Task), each automatic retry must name a **changed condition** — identical signature ⇒ replan/escalate, never a blind loop; rework always in a **new Attempt, clean worktree** with the failed Attempt's diff preserved as evidence. Quota exhaustion with a pinned model class ⇒ `WAITING_RESOURCE` (Never silent cheaper-model substitution; alternatives only when they satisfy the Work Order's pinned requirement). Crash reconciliation walks durable state → event history → RUNNING Attempts → worker leases (E3 `WorkerLease.expiresAt`), reconnecting live workers and interrupting the rest — success is never claimed without completion evidence. Recovery operations are idempotent (`recover:{attemptId}:{k}` keys; duplicates no-op).

6. **Emergency stop is durable, graceful, evidence-preserving, human-resumed.** `emergencyStop()` sets a durable flag + event; blocks assignment/provisioning and all consequential external side effects (`check` short-circuits `DENY`); requests graceful worker cancellation (bounded grace, then forceful); interrupts in-flight Attempts as `interrupted` (distinct from `FAILED`/`CANCELLED`) while preserving all state and evidence; requires an explicit operator `resume()` with recorded identity. Pause/resume/e-stop are the §10 control set.

## Alternatives considered

- **Leaf-decides-with-validation** (most specific policy level wins; runtime validates it never loosens the parent): rejected — the guarantee would depend on every future writer validating correctly; strictest-wins makes widening structurally impossible, and the validation burden disappears.
- **Default-permissive with deny-lists** (capabilities granted unless denied): rejected — sensitive actions (`secrets.read`, `production.write`, production deploys) default-deny is the safer and simpler-to-audit invariant; permissive defaults make the `REQUIRE_HUMAN` tier gate the only brake, and a bug there is silent.
- **Cross-join decision matrix instead of narrow-and-fold** (each level must restate all capabilities for the child to inherit): rejected — unwieldy and error-prone; inheritance with fold keeps each level small while remaining provably non-widening.
- **LLM-assisted risk classification**: rejected for v0.1 — `classifyRisk` must be deterministic and auditable (it gates the tier); LLM opinion could enter only as advisory evidence for a human.

## Consequences

- **Positive:** the policy engine is small, pure and provable child ⊆ parent by construction; every sensitive action is auditable end-to-end (durable `policy_decisions` keyed to tasks/attempts); risk posture can only ratchet upward through evidence, never silently downward; the recovery engine gets a fixed vocabulary that tests can pin.
- **Negative:** strictest-wins means a stale Org `DENY` silently suppresses Project grants (documented, auditable via the `rules` trail, but operators must maintain the root policy); the closed capability list needs an ADR revision to extend; ceilings make some conceivable legal-but-bare-`ALLOW` production flows impossible without an operator in the loop — that is the point.
- **Flagged to the controller (E1 vocabulary gaps, respected not modified here):** v0.1 records `WAITING_RESOURCE` as an Attempt outcome + event (Task stays `RUNNING`, blocked in place) and reconciles e-stop interrupts through the lease path, because the E1 Task/WorkOrder state vocabularies have no `CANCELLING`/`CANCELLED`/`WAITING_RESOURCE` states; extending spec §5 state machines is a deferred E1 follow-up.
- **Later:** #23 implements and tests the above contract; E8 consumes `policy_decision` records as telemetry (`allow/deny/gate` outcomes are already a named telemetry dimension); the policy YAML loader + Client editor are follow-ups to the embedded v0.1 defaults.
